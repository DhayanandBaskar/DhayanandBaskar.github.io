Room Rental with Unreliable Inventory and Revolut Payments

A booking saga built around inventory holds, payment authorisation, compensation, reconciliation, and explicit consistency boundaries.

  • Payments
  • Sagas
  • Consistency
  • Third-party APIs

The core challenge is not payment or search. It is this invariant:

Never tell the customer a room is confirmed unless the third party has reserved it and payment has succeeded—or a compensating action is guaranteed.

The first question I would ask is:

Does the inventory provider support an atomic hold with TTL, confirm, cancel, idempotency key, and reservation-status lookup?

If it does, we can build a reliable booking saga. If it doesn’t, we cannot guarantee zero overbooking because the authoritative inventory is outside our control. We must present the booking as pending until the provider confirms it.

1. Requirements

Functional

  1. Customers search rooms by location, dates and occupancy.
  2. Search results show fixed prices and recent availability.
  3. Customers initiate a booking for one room and date range.
  4. The system temporarily holds the room while payment is completed.
  5. Payment is handled through the Revolut Merchant API.
  6. The booking becomes confirmed only when:
    • Revolut authorises the payment.
    • The third party confirms the room.
    • We capture the payment.
  7. Failed or abandoned bookings release the inventory hold.
  8. Customers can view their booking status.
  9. Customers can cancel according to the cancellation policy.
  10. Operations can inspect and reconcile stuck bookings.

Clarifications

  • Is the price fixed per night or per complete stay?
  • Are taxes and fees included?
  • How long can inventory be held—10 or 15 minutes?
  • Can the supplier atomically hold and confirm inventory?
  • Can supplier requests carry our booking ID as an idempotency/reference key?
  • Can we query a reservation by that reference after a timeout?
  • What is the cancellation/refund policy?
  • Is immediate confirmation required, or is PENDING_CONFIRMATION acceptable?
  • What scale and geographical coverage are expected?

Non-functional

I would propose:

  • Search latency: P95 under 300 ms.
  • Booking initiation: P95 under two seconds, excluding customer payment time.
  • No locally generated overlapping active bookings.
  • Never capture payment before the room is confirmed.
  • Retried customer, supplier and payment requests must be idempotent.
  • Search may be eventually consistent.
  • Booking and payment state require durable, strongly consistent storage.
  • Supplier outages must not corrupt booking or payment state.
  • Complete audit trail for every state transition and external request.
  • 99.9% booking API availability, while checkout fails closed if inventory cannot be verified.

2. Capacity

I would ask for numbers, then use assumptions if none are provided:

100,000 rooms
1,000 search requests/second at peak
20 booking attempts/second at peak
15-minute inventory holds

This is read-heavy. Search needs cached inventory, but booking correctness does not require microservices or Kafka.

5. Architecture

One deployable application:

Web/mobile clients
        |
Stateless Room Booking application
  - Search API
  - Booking API
  - Supplier adapter
  - Revolut adapter/webhook
  - Booking workflow worker
        |
PostgreSQL + optional Redis search cache

External dependencies:

  • Unreliable inventory provider
  • Revolut Merchant API
  • Email/push provider

The worker can run separately for operational reasons but remains part of the same application and data model.

6. Search flow

  1. A scheduled synchronisation worker fetches availability from the supplier.
  2. Results are stored with fetched_at and optionally cached in Redis.
  3. Search is served from our cache rather than calling the unreliable supplier for every request.
  4. Results are labelled as subject to final confirmation.
  5. Checkout always asks the supplier for an authoritative hold.

If the inventory feed is stale:

  • Search may still display results with a staleness limit.
  • Checkout fails closed if an authoritative hold cannot be acquired.
  • We do not confirm from cached inventory.

7. Booking and payment flow

I would use Revolut’s manual capture mode: first reserve the customer’s funds, confirm the room, and only then capture the money. Revolut explicitly recommends manual capture when inventory must be verified before fulfilment. Revolut manual-capture guide

sequenceDiagram
    actor C as Customer
    participant B as Booking application
    participant D as PostgreSQL
    participant I as Inventory provider
    participant R as Revolut Merchant API

    C->>B: POST /bookings + Idempotency-Key
    B->>D: Create INITIATED booking
    B->>I: Hold room for 15 minutes<br/>reference = bookingId
    I-->>B: holdId + expiresAt
    B->>D: INVENTORY_HELD

    B->>R: Create order<br/>manual capture<br/>reference = bookingId
    R-->>B: orderId + checkoutUrl
    B->>D: AWAITING_PAYMENT
    B-->>C: checkoutUrl

    C->>R: Complete checkout
    R-->>B: ORDER_AUTHORISED webhook
    B->>R: Retrieve and verify order
    B->>D: PAYMENT_AUTHORISED

    B->>I: Confirm hold
    I-->>B: providerBookingId
    B->>D: INVENTORY_CONFIRMED

    B->>R: Capture authorised order
    R-->>B: ORDER_COMPLETED webhook
    B->>D: CONFIRMED
    B-->>C: Booking confirmed

Why this order?

  • Holding inventory before payment reduces the chance that the room disappears during checkout.
  • Authorising rather than capturing prevents charging the customer before supplier confirmation.
  • Confirming inventory before capture avoids refunds for normal availability failures.
  • If confirmation fails, cancel the uncaptured Revolut order and release the authorisation.
  • If capture fails after inventory confirmation, cancel the supplier booking or enter MANUAL_REVIEW.

Revolut orders can move through pending, processing, authorised and completed; failed payment attempts may return the same order to pending, allowing another attempt. Therefore, ORDER_PAYMENT_FAILED does not automatically mean the whole booking has failed. Official order lifecycle

8. Payment implementation

Create a Revolut order approximately like:

{
  "amount": 30000,
  "currency": "GBP",
  "capture_mode": "manual",
  "merchant_order_data": {
    "reference": "booking-123"
  },
  "description": "Room booking booking-123"
}

Persist the returned revolut_order_id and checkout URL.

If order creation times out after Revolut may have accepted it:

  1. Do not blindly create another order.
  2. Query Revolut using our merchant order reference.
  3. Reuse the existing order if found.
  4. Create a new one only when absence is established.

The Merchant API supports filtering orders by the merchant’s reference, which makes this reconciliation possible. Revolut Merchant API

Webhooks

The webhook handler:

  1. Reads the unmodified request body.
  2. Verifies the HMAC signature.
  3. Verifies that the timestamp is within the allowed tolerance.
  4. Stores the webhook.
  5. Responds immediately.
  6. Processes it asynchronously.
  7. Retrieves the current Revolut order before advancing booking state.

Revolut says webhook ordering is not guaranteed and failed delivery is retried, so our workflow must depend on current order state—not webhook arrival order. Webhook behaviour

Revolut signs callbacks using Revolut-Signature and Revolut-Request-Timestamp; its documentation recommends HMAC-SHA256 verification and a five-minute timestamp tolerance. Webhook signature verification

9. Idempotency

There are several different invariants—not one generic “idempotency” check.

Customer retry

UNIQUE (user_id, client_idempotency_key)

Store the request hash. The same key plus the same request returns the original booking. The same key with different dates returns 409 Conflict.

Local overlap protection

PostgreSQL can prevent two active local bookings whose date ranges overlap for the same supplier room:

EXCLUDE USING gist (
  provider_room_id WITH =,
  daterange(check_in, check_out, '[)') WITH &&
)
WHERE (
  status IN (
    'INVENTORY_HELD',
    'AWAITING_PAYMENT',
    'PAYMENT_AUTHORISED',
    'INVENTORY_CONFIRMED',
    'CAPTURING_PAYMENT',
    'CONFIRMED'
  )
);

This prevents our own system from creating overlapping reservations. It cannot prevent another seller using the same third-party inventory—that requires the supplier’s atomic hold.

Supplier operations

Every hold/confirm/cancel request carries booking_id as its external reference.

After an ambiguous timeout:

  • Query supplier status by booking_id.
  • Retry only if the previous request definitely did not succeed.
  • If the supplier offers neither idempotency nor status lookup, transition to MANUAL_REVIEW; blind retries could double-book.

Payment operations

UNIQUE (revolut_order_id)
UNIQUE (booking_id)

Only one Revolut order is active for a booking. State transitions use compare-and-set/version checks. Revolut documents capture as idempotent for repeated requests with the same amount. Capture semantics

10. Unreliable supplier failure modes

Availability endpoint down

  • Serve sufficiently fresh cached search results.
  • Mark them as subject to confirmation.
  • Do not accept checkout if a hold cannot be obtained.

Hold request times out

The result is unknown. Query by our booking reference before retrying.

Supplier is down after payment authorisation

  • Retry confirmation with bounded backoff until shortly before hold expiry.
  • If it cannot be confirmed, cancel the Revolut order and release the hold.
  • Tell the customer the booking could not be confirmed.

Supplier confirms, but response is lost

Query reservation status by booking_id. Never issue another reservation blindly.

Supplier confirms, Revolut capture fails

  • Reconcile the Revolut order.
  • If definitively uncaptured, cancel the supplier booking.
  • If either result remains ambiguous, use MANUAL_REVIEW.
  • Never display CONFIRMED until reconciled.

Revolut webhook is missing

A reconciliation worker polls Revolut for non-terminal payments whose state has not changed within the expected window.

Customer abandons checkout

When the 15-minute timer expires:

  • Cancel the pending or authorised Revolut order.
  • Release the supplier hold.
  • Mark the booking CANCELLED.

11. What if the supplier has no hold API?

Then I would say this explicitly:

We cannot promise availability during payment because the source of truth provides no reservation primitive.

The fallback flow is:

  1. Create a Revolut order with manual capture.
  2. Customer authorises payment.
  3. Attempt an atomic supplier booking.
  4. On success, capture payment.
  5. On failure, cancel the authorisation.

This protects the customer from being charged without a room, but some checkout attempts will fail after payment authorisation because inventory may disappear during the flow. That is a limitation of the supplier contract, not something local locks or Kafka can solve.

12. Trade-offs and scaling

I would not start with separate Search, Booking, Inventory and Payment services.

Start with:

  • One stateless application
  • PostgreSQL
  • Optional Redis for search
  • Database-backed workflow jobs
  • Supplier and Revolut adapters

Split later only when justified:

  • Search/synchronisation scales independently at high read volume.
  • Booking remains strongly consistent around its database.
  • A durable broker replaces the database job table at much higher workflow volume.
  • Supplier adapters can be separated if many providers have different failure behaviours.

The deep dive here is not infrastructure breadth. It is the hold → authorise → confirm → capture saga, its idempotency boundaries, and its compensation paths. That is where I would spend most of the interview.
