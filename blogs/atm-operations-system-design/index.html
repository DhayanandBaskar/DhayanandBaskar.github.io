Designing a Reliable ATM Operations System

A simple, structured design for ATM telemetry, maintenance tasks, agent assignment, concurrency, and failure recovery.

  • API Design
  • Data Modelling
  • Concurrency
  • Idempotency

I would design it as one stateless ATM Operations application, one PostgreSQL database, one background worker, and an external notification provider. No orchestrator, separate User Service, ATM Tracker, Task Service, SNS or SQS in the initial design.

The point of the interview would be to make the requirements, behaviours, APIs, data model and concurrency rules unmistakably clear before discussing extensions.

1. Clarify the problem

I would begin with these questions:

  • Does an ATM report only its total cash, or cash by currency and denomination?
  • What conditions create a task: low cash, hardware error and missed heartbeat?
  • Can an ATM have a refill and repair task simultaneously?
  • Is assignment automatic or performed by a manager?
  • Does an agent handle only one active task?
  • What proves completion: the agent’s confirmation, or subsequent ATM telemetry?
  • How frequently do ATMs report?
  • Is routing explicitly out of scope?
  • Do we design only for five ATMs, while leaving a path to future growth?

I wouldn’t need to know the word “cassette.” If denominations matter, the telemetry can simply contain:

{
  "cash": [
    { "currency": "GBP", "denomination": 10, "noteCount": 100 },
    { "currency": "GBP", "denomination": 20, "noteCount": 200 }
  ]
}

2. Functional requirements

After receiving answers, I would write these as explicit system behaviours:

  1. ATMs periodically report operational status, cash inventory and errors.
  2. Managers can view each ATM’s latest status, cash and active tasks.
  3. The system creates a refill task when the configured cash rule is violated.
  4. The system creates a repair task for an ATM error or missed heartbeat.
  5. The system must not create a duplicate active task for the same ATM and task type.
  6. The system automatically assigns an unassigned task to an available agent.
  7. An agent can fetch, acknowledge, start and complete their assigned task.
  8. An agent cannot have more than one active assignment.
  9. Only the assigned agent or a manager may modify a task.
  10. The system notifies an agent after assignment.
  11. Task completion is recorded and optionally verified using subsequent ATM telemetry.
  12. Route optimization is out of scope.

3. Non-functional requirements

I would propose numbers and ask the interviewer to confirm them:

  • Five ATMs, ten agents, one heartbeat every five minutes.
  • Low-cash/error tasks created within 30 seconds of receiving telemetry.
  • An ATM becomes OFFLINE after two missed heartbeats—approximately ten minutes.
  • Dashboard reflects accepted telemetry within five seconds.
  • Strong consistency for task creation, assignment and state transitions.
  • Eventual consistency is acceptable for dashboard presentation and notifications.
  • Accepted tasks must survive application restarts.
  • Retried telemetry and commands must be idempotent.
  • 99.9% availability is sufficient.
  • ATM devices require device credentials; employees require RBAC.
  • Every assignment and task transition must be auditable.

Capacity

Five heartbeats every five minutes is:

5 / 300 = 0.017 requests per second

Even 5,000 ATMs would average only about 17 heartbeat requests per second. Therefore, a stateless application and PostgreSQL are comfortably sufficient. I would run two instances for availability, not because throughput demands it.

The API and worker can use the same codebase and deployment. They are logical components, not independent microservices.

7. Walk through the critical flow

ATM telemetry to task creation

  1. The ATM sends telemetry with an eventId and monotonically increasing sequenceNumber.
  2. The application authenticates the ATM.
  3. In one database transaction:
    • Insert the telemetry event.
    • If the event already exists, return the previous success.
    • Ignore an older sequence number.
    • Update the current ATM state and cash inventory.
    • Evaluate refill and repair rules.
    • Attempt to create the appropriate task.
  4. Commit.
  5. An assignment worker finds the newly created task and an available agent.
  6. It assigns them atomically.
  7. The notification provider alerts the agent.
  8. The mobile application fetches the authoritative task from the API.

The push notification is only a hint. Losing it does not lose the task.

Missed heartbeat

A background worker periodically checks:

last_seen_at < now() - 10 minutes

It marks the ATM offline and attempts to create a repair task using the same database uniqueness rule.

8. Robust idempotency and concurrency

This is where I would do the main technical deep dive.

Duplicate delivery

A retried telemetry event is deduplicated by:

UNIQUE (atm_id, device_event_id)

This is message idempotency.

Duplicate business task

A partial unique constraint prevents multiple active tasks:

CREATE UNIQUE INDEX one_active_task_per_atm_type
ON task (atm_id, type)
WHERE status IN (
  'CREATED',
  'ASSIGNED',
  'ACKNOWLEDGED',
  'IN_PROGRESS',
  'PENDING_VERIFICATION'
);

This is a business invariant. It is different from event deduplication.

Two application instances may simultaneously attempt to create the same task. One insert succeeds; the other conflicts and safely returns the existing task. There is no read-then-insert race.

One task per agent

Another partial unique constraint protects assignment:

CREATE UNIQUE INDEX one_active_task_per_agent
ON task (assignee_id)
WHERE assignee_id IS NOT NULL
  AND status IN (
    'ASSIGNED',
    'ACKNOWLEDGED',
    'IN_PROGRESS'
  );

The assignment worker can use FOR UPDATE SKIP LOCKED to claim tasks and agents concurrently, with the constraint as the final protection.

Completion validation

UPDATE task
SET status = 'COMPLETED',
    completed_at = NOW(),
    version = version + 1
WHERE id = :task_id
  AND assignee_id = :authenticated_agent
  AND status IN ('ACKNOWLEDGED', 'IN_PROGRESS')
  AND version = :expected_version;

If zero rows are updated, the request is stale, unauthorized or an invalid transition. A unique commandId makes retries return the original outcome.

9. Failure behaviour

  • Application instance fails: another instance handles requests.
  • ATM times out waiting: it retries using the same eventId.
  • Assignment worker fails: the unassigned task remains durable in PostgreSQL.
  • Notification provider fails: the task still exists; the agent app fetches it.
  • Agent does not acknowledge: release the assignment after a lease timeout.
  • Database fails: the system temporarily stops accepting changes, but committed tasks survive.
  • Agent falsely completes a task: optionally use PENDING_VERIFICATION until the ATM reports healthy status and updated cash.

If notification reliability requires more than retries, I would then introduce an outbox table and relay inside this same application. I would not begin the design with an external event platform.

10. Scaling discussion

For 5,000 ATMs:

  • Add stateless application instances.
  • Add worker instances using SKIP LOCKED.
  • Index atm.last_seen_at, task status and assignee.
  • Add a read replica only if dashboard traffic requires it.

For millions across countries:

  • Partition ATM ownership by region or country.
  • Give each region its own ingestion/application/database stack.
  • Publish regional summaries to a global dashboard.
  • Introduce a durable event platform where regional decoupling becomes valuable.
  • Address data residency and regional failover.

That is an extension of the simple design, not the starting point.
